## Design Context

### Users

The documentation serves two audiences equally:

- Platform engineers who install, configure, secure, operate, upgrade, and troubleshoot the operator on OpenShift and other Kubernetes distributions connected to Azure.
- Application developers who request workload identities, bind them to Kubernetes ServiceAccounts, validate token exchange, and recover retained identities safely.

Readers are usually solving an infrastructure task and need to understand both the immediate command to run and the trust or ownership boundary behind it. The site must make the supported path obvious without hiding the operational detail needed during incidents and reviews.

### Brand Personality

Authoritative, calm, and precise. The interface should inspire confidence in security-sensitive infrastructure while remaining approachable to readers who are new to workload identity. Copy is direct, specific, and free of promotional language.

### Aesthetic Direction

Use a refined editorial-technical direction with a restrained Azure-inspired palette. Prefer generous whitespace, strong typographic hierarchy, crisp diagrams, and deliberate asymmetry over dashboard-like card grids. The experience must feel like a carefully maintained open-source technical manual, not an Azure portal imitation or an untouched Docusaurus starter.

Support polished light and dark themes. Use color to communicate trust boundaries, ownership, lifecycle state, and navigational hierarchy. Avoid neon-on-dark styling, generic blue-purple gradients, glassmorphism, decorative code motifs, and excessive rounded cards.

Meet WCAG 2.2 AA for color contrast, keyboard navigation, focus visibility, semantics, and motion. Respect reduced-motion and high-contrast preferences. Critical content and navigation must remain available at narrow viewport widths.

### Design Principles

1. **Lead readers to a verified outcome.** Start task-oriented pages with prerequisites, the supported path, verification, and safe rollback or cleanup.
2. **Reveal the trust model.** Use concise diagrams and explicit ownership language wherever Kubernetes, the operator, OpenShift, and Azure interact.
3. **Serve both depths.** Give application developers a short golden path while linking platform engineers to configuration, failure modes, and architectural rationale.
4. **Make status legible.** Use consistent visual and written patterns for prerequisites, warnings, destructive actions, compatibility, and resource conditions.
5. **Prefer durable clarity.** Keep styling restrained, examples source-controlled, navigation predictable, and documentation close to the behavior it describes.
